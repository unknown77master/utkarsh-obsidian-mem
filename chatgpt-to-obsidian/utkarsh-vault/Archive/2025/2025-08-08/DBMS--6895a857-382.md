### **Q: List the main characteristics of the database approach and explain how it differs from the traditional file system.**

---

### **1. Main Characteristics of the Database Approach**

The **Database Approach** refers to managing data using a Database Management System (DBMS). Its main characteristics are as follows:

| **Characteristic** | **Description** |
|-----------------------------------------|-----------------|
| **1. Data Abstraction** | DBMS provides multiple levels of data abstraction — physical, logical, and view levels — to separate storage details from users. |
| **2. Data Independence** | Changes in the data schema do not affect application programs (Logical and Physical data independence). |
| **3. Reduced Data Redundancy** | Data is stored centrally, which reduces duplication across the system. |
| **4. Enhanced Data Integrity** | Constraints (e.g., primary key, foreign key, domain) maintain accuracy and consistency of data. |
| **5. Improved Data Security** | Access controls and authorization levels can be defined for different users. |
| **6. Concurrency Control** | Multiple users can access data simultaneously without conflicts, using transaction management. |
| **7. Backup and Recovery** | Automatic recovery and backup mechanisms help ensure data safety in case of failure. |
| **8. Centralized Management** | Data and its management logic are centralized, making the system easier to administer. |
| **9. Support for Multiple Views** | Different users can have customized views of the same data, tailored to their needs. |
| **10. Query Optimization and Processing** | Efficient query execution using query optimization and indexing techniques. |

---

### **2. Difference Between Database Approach and Traditional File System**

| **Aspect** | **Traditional File System** | **Database Approach (DBMS)** |
|-----------------------------|--------------------------------------------------------------------|---------------------------------------------------------------------|
| **Data Redundancy** | High, same data may be repeated in multiple files | Low, due to centralized storage and normalization |
| **Data Sharing** | Limited, files are typically owned by one application | High, multiple users and applications can access same data |
| **Data Integrity** | Difficult to enforce across multiple files | Enforced via constraints in DBMS |
| **Security** | Poor, no fine-grained access control | Strong security features (roles, privileges, encryption) |
| **Data Independence** | No separation between data and programs | High, application logic is independent of schema |
| **Concurrency Control** | Not supported | Supported via ACID-compliant transactions |
| **Backup & Recovery** | Manual and error-prone | Automatic and efficient |
| **Scalability** | Difficult to scale and manage large data | Easily scalable and maintainable |
| **Querying** | No standardized query language, needs custom code | SQL support for powerful, declarative querying |
| **Maintenance** | Hard to update or maintain files | Easier to maintain with built-in tools and interfaces |

---

### **Conclusion** 
The database approach offers a more structured, consistent, and scalable way of handling data compared to the traditional file-based systems. It improves data management by minimizing redundancy, enhancing security, and enabling efficient querying and multi-user support.

# **CAP Theorem in Distributed Applications**

## **Introduction**
The CAP Theorem is an important concept in distributed database systems and distributed applications. It was proposed by **Eric Brewer** and is also called **Brewer’s Theorem**.

The theorem states that:

> A distributed system can provide at most two out of the following three properties simultaneously:
1. **Consistency (C)**
2. **Availability (A)**
3. **Partition Tolerance (P)**

---

# **1. Consistency (C)**

Consistency means:
> Every user gets the most recent and correct data at the same time.

After updating data in one node, all other nodes should immediately reflect the same updated data.

### Example
If a bank account balance is updated on one server, all users accessing other servers should see the same balance instantly.

---

# **2. Availability (A)**

Availability means:
> Every request receives a response, even if some servers fail.

The system should always remain operational and accessible.

### Example
If one server crashes, another server should still provide data to users.

---

# **3. Partition Tolerance (P)**

Partition tolerance means:
> The system continues working even if communication failure occurs between distributed nodes.

A network partition happens when servers cannot communicate with each other.

### Example
If two data centers lose network connection, the system should still continue functioning.

---

# **Understanding CAP Theorem**

In distributed systems, network failures are unavoidable. Therefore, Partition Tolerance is generally necessary.

Hence, during partition, the system must choose between:
- Consistency
OR
- Availability

It cannot guarantee both together.

---

# **Possible Combinations**

## **1. CP System (Consistency + Partition Tolerance)**

- System maintains correct and consistent data
- Some requests may be rejected during network failure

### Example
Distributed banking systems

### Advantage
High data accuracy

### Disadvantage
Reduced availability

---

## **2. AP System (Availability + Partition Tolerance)**

- System always responds to requests
- Different nodes may temporarily contain different data

### Example
Social media applications

### Advantage
High availability

### Disadvantage
Temporary inconsistency

---

## **3. CA System (Consistency + Availability)**

- Provides consistent and available data
- Does not tolerate network partition

This combination is suitable only for centralized systems, not large distributed systems.

---

# **Importance of CAP Theorem in Distributed Application Development**

CAP theorem helps developers choose system design according to application requirements.

---

## **For Banking Systems**
- Consistency is more important
- Wrong balance cannot be shown

So CP systems are preferred.

---

## **For Social Media or E-commerce**
- Availability is more important
- Small delay in synchronization is acceptable

So AP systems are preferred.

---

# **Advantages of CAP Theorem**
1. Helps design reliable distributed systems 
2. Assists in selecting database architecture 
3. Improves scalability decisions 
4. Clarifies trade-offs in distributed applications 

---

# **Limitations**
1. Cannot achieve all three properties fully at the same time 
2. Real-world systems often require compromise 
3. Complex to implement in large-scale systems 

---

# **Conclusion**
The CAP theorem explains the trade-off between Consistency, Availability, and Partition Tolerance in distributed systems. During network partition, a distributed application must choose either consistency or availability. Therefore, CAP theorem plays an important role in designing modern distributed databases and cloud-based applications.

# **Atomicity Using Recovery Methods**

## **Atomicity**
Atomicity is one of the ACID properties of a transaction.

It states that:
> A transaction is either completely executed or not executed at all.

If a failure occurs during transaction execution, all partial changes made by the transaction must be undone.

---

# **Ensuring Atomicity Using Recovery Methods**

Recovery methods help restore the database to a consistent state after:
- System crash
- Power failure
- Transaction failure

Atomicity is ensured by:
1. Keeping track of all transaction operations 
2. Undoing incomplete transactions 
3. Redoing committed transactions if required 

This is mainly achieved using:
- Log-based recovery
- Shadow paging

---

# **Log-Based Recovery Method**

## **Definition**
Log-based recovery uses a special file called a **log file** to store details of all database operations performed by transactions.

The log helps recover the database after failures.

---

# **Contents of Log File**

The log file contains records such as:
```text id="d3or9j"
<Transaction_ID, Data_Item, Old_Value, New_Value>
```

It also stores:
- Start of transaction
- Commit operation
- Abort operation

---

# **Types of Log Records**

## **1. Start Record**
Indicates transaction execution has started.

Example:
```text id="iq0spm"
<START T1>
```

---

## **2. Update Record**
Stores old and new values.

Example:
```text id="n0g1op"
<T1, X, 100, 200>
```

Meaning:
- Old value of X = 100
- New value of X = 200

---

## **3. Commit Record**
Indicates successful completion of transaction.

Example:
```text id="h8xyvq"
<COMMIT T1>
```

---

## **4. Abort Record**
Indicates transaction failure.

Example:
```text id="x1t5xw"
<ABORT T1>
```

---

# **Working of Log-Based Recovery**

---

# **Step 1: Transaction Starts**
A start record is written into log.

```text id="wwjlwm"
<START T1>
```

---

# **Step 2: Data Modification**
Whenever data is updated:
- Old value
- New value

are written into log before updating database.

Example:
```text id="q2ql8d"
<T1, A, 500, 700>
```

---

# **Step 3: Commit Transaction**
If transaction completes successfully:
```text id="n2rk0d"
<COMMIT T1>
```

is written into log.

---

# **Step 4: Recovery After Failure**

### Case 1: Transaction Committed Before Failure
- REDO operation is performed
- Ensures committed changes are reflected in database

---

### Case 2: Transaction Not Committed Before Failure
- UNDO operation is performed
- Restores old values using log

---

# **Types of Log-Based Recovery**

---

# **1. Deferred Database Modification**

## Concept
- Database is updated only after commit
- During recovery:
 - REDO committed transactions
 - No UNDO needed

---

# **2. Immediate Database Modification**

## Concept
- Database may be updated before commit
- During recovery:
 - UNDO incomplete transactions
 - REDO committed transactions

Most commonly used method.

---

# **Write Ahead Logging (WAL)**

## Rule
> Log record must be written to stable storage before actual database modification.

This ensures recovery information is always available.

---

# **Advantages of Log-Based Recovery**
1. Ensures atomicity and durability 
2. Prevents data inconsistency 
3. Supports crash recovery 
4. Reliable transaction management 

---

# **Disadvantages**
1. Additional storage required for logs 
2. Recovery process may take time 
3. Log maintenance overhead 

---

# **Conclusion**
Log-based recovery is an important recovery mechanism used to ensure atomicity in DBMS. It maintains transaction logs containing old and new values of data items. During system failure, committed transactions are redone and incomplete transactions are undone, thereby restoring database consistency and ensuring reliable transaction processing.

# **Deadlock in DBMS**

## **Definition**
A deadlock occurs when two or more transactions wait indefinitely for each other to release resources.

In this situation, none of the transactions can proceed further.

---

# **Example of Deadlock**

Suppose:

- Transaction T1 locks data item X and requests Y 
- Transaction T2 locks data item Y and requests X 

Now:
- T1 waits for T2
- T2 waits for T1

Neither transaction can continue.

This situation is called deadlock.

---

# **When Does Deadlock Happen?**

Deadlock occurs when the following four conditions hold simultaneously:

---

## **1. Mutual Exclusion**
A resource can be used by only one transaction at a time.

---

## **2. Hold and Wait**
A transaction holds one resource and waits for another resource.

---

## **3. No Preemption**
Resources cannot be forcibly taken away from a transaction.

---

## **4. Circular Wait**
Transactions form a circular chain where each transaction waits for a resource held by another.

Example:
```text id="a5wp3m"
T1 waits for T2
T2 waits for T3
T3 waits for T1
```

---

# **Deadlock Prevention**

Deadlock prevention ensures that at least one deadlock condition never occurs.

---

# **Methods to Prevent Deadlock**

---

## **1. Eliminate Hold and Wait**
A transaction must request all required resources at once before execution.

### Advantage
Prevents waiting condition.

### Disadvantage
Resource utilization becomes poor.

---

## **2. Resource Ordering**
Assign an order to resources and transactions must request resources only in that order.

### Example
If:
```text id="4l5dr5"
X < Y < Z
```

Then transactions must request:
```text id="c5mdjq"
X → Y → Z
```

This prevents circular wait.

---

## **3. Allow Preemption**
If a transaction cannot get requested resource, it releases currently held resources.

---

## **4. Timestamp-Based Prevention**

### Wait-Die Scheme
- Older transaction waits
- Younger transaction aborts

---

### Wound-Wait Scheme
- Older transaction forces younger transaction to abort
- Younger transaction waits

---

# **Deadlock Detection**

Instead of prevention, the system allows deadlocks and periodically checks for them.

---

## **Wait-For Graph**

- Each node represents a transaction
- Edge:
```text id="n9kqoo"
Ti → Tj
```
means Ti waits for Tj.

### Rule
If graph contains a cycle → deadlock exists.

---

# **Deadlock Recovery**

After detecting deadlock, the system must recover.

---

# **Recovery Methods**

---

## **1. Transaction Rollback**
Abort one or more transactions to break deadlock.

### Types
- Total rollback
- Partial rollback

---

## **2. Transaction Termination**
Terminate one transaction completely.

Victim transaction is selected based on:
- Priority
- Amount of work done
- Number of resources held

---

## **3. Resource Preemption**
Take resource away from one transaction and allocate to another.

---

# **Advantages of Deadlock Handling**
1. Prevents indefinite waiting 
2. Improves system reliability 
3. Ensures smooth transaction execution 

---

# **Disadvantages**
1. Detection algorithms increase overhead 
2. Rollbacks waste processing time 
3. Prevention techniques reduce concurrency 

---

# **Conclusion**
Deadlock occurs when transactions wait indefinitely for resources held by each other. It can be handled using prevention, detection, and recovery techniques. Deadlock management is essential in DBMS to maintain efficient and reliable transaction processing.
